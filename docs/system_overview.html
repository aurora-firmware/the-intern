The Intern: system overview

The Intern is an agent that works for a team. One daemon on a machine the team keeps running takes jobs from anyone who can reach it and sees each one through: define it, get what is missing, act, verify. Agents made from roles do the work in conversations kept in one pi-durable database, with one lead agent per job. Clients, job sources and agent tools all use the same service layer. This document is the map: the shared vocabulary, the shape of the system, and which spec owns which part.

S-000, specs and accepted ADRs win over this document contains no requirements updated with every spec that changes a shared term or the spec map

1 · Scope and principles

One team, one machine, one process

The Intern works unattended for a team, from a machine the team keeps running. It is one TypeScript package that embeds pi as a library on @earendil-works/pi-durable. S-000 is the source of truth for scope.

In scope

  • Equal team members: anyone who can reach a way in. No logins.
  • Ways in: the command line, a web interface on the team's network, and The Intern's own mailbox.
  • Jobs from requests, schedules, triggers and follow-ups, many at once.
  • One OS account, the installing person's in v1, on Linux (x64) and macOS (Apple silicon), started at machine startup.

Out of scope

  • Logins, per-person permissions and approval rules for actions.
  • Hosting the wiki, footholds on other machines, tracker sync, chat apps in v1.
  • Code extensions; Windows, Linux arm64 and Intel macOS.
  • Database compatibility across pi versions; the job record moves by export and import.

Principles that hold across all specs

PrincipleWhat it means
One owner per databaseAt most one daemon opens an instance's database. Nothing else reads or writes it; clients read history through the service layer.
Durability belongs to the runtimeResume, exactly-once input, queued input and checkpoints come from pi-durable. We write no retry loops, intake tables or recovery code, with one bounded exception: the facts The Intern owns about a conversation (held messages, awaiting links, creation keys) live in its own documents, and the only recovery is redelivering what they show as undelivered, safe to repeat through pi-durable request ids (ADR-001).
The service account is the boundaryThe Intern runs as one OS account. Directories are 0700 and files owner-only. We store no credentials: models, keys and accounts are that account's, used in place. What agents can do is bounded by what that account can reach.
pi-durable sits behind a narrow hostOnly the host module and our own pi-durable extensions import it. An upgrade touches a few files.
Transport-free service layerEvery capability is a named operation marked read or control. A new listener never changes an operation. No listener authenticates callers.
Clients are viewersNo connection owns work. Closing or lagging never stops or slows an agent run.
One lead per jobEach job has one lead conversation; its agent is the only lead and the only one that closes the job. No agent owns another: an agent of any role can hand off to, or invoke, any role.
Unattended except a blocked jobNo step waits for a human, except a blocked job waiting for the answer to its question. A blocked job holds no worker thread.
Fail closed on the membraneInvalid configuration stops startup; a storage error ends the process and the supervisor restarts it.
2 · The system at a glance

Everything goes through the service layer

The daemon is the only process that touches the database. The command line, the web interface, email, schedules and agent tools are different callers of the same operations.

3 · Jobs, roles, agents and conversations

A role is the base context; an agent applies it in a conversation of a job

  • Every job has one lead conversation; its current agent is the job's lead.
  • Every conversation belongs to one job and has exactly one agent at a time.
  • A role defines the context where an agent starts. Team members shape roles.
  • Agents change by handoff (same conversation; in the lead conversation it passes the lead) or spread by invocation (new conversations of the same job).
  • Invoked agents do parts of the job and report back; only the lead closes the job.
  • Nothing here is an operating-system process.

Blocked jobA job waiting for the answer to its question. Its lead conversation is parked and holds no worker thread.
Definition of done, evidenceWhat the lead checks the result against before closing a job, and what it closes the job with.
Follow-up jobA job an agent creates for work it noticed while working on another.
Job source, originWhat starts a job and its lead conversation: a request, a schedule fire, a trigger or a follow-up. A conversation's origin records its job source, or the invoking conversation.
Schedule, triggerA schedule starts jobs at set times, fresh or with the history of its last runs. A trigger starts a job when an event happens, such as a job outcome or mail arriving.
Lead conversation, lead agentEach job's one lead conversation; its current agent carries the job from definition to verification and is the only one that closes it.
Specialist role, specialist agentA role suited to a kind of work (any role a team creates); an agent of it invoked for part of a job.
Team knowledgeThe knowledge sources The Intern reads and keeps current: the team's wiki (run by the team), repository docs and other folders.
RoleThe base context an agent starts from: instructions, tools, skills and default model, thinking level and workspace. Shipped (bob, gp) or created by the team.
AgentThe application of a role in a conversation, and the actor that interacts with the model there. It exists only within a conversation, one at a time, and can be configured during it. Not an operating-system process.
SeatThe place of the current agent in a conversation, with its role, model, thinking level and workspace (defaults or overrides).
ConversationThe pi-durable meaning: an ordered transcript of entries with its own pi-durable agent. Each belongs to one job.
Transcript, contextThe transcript is every stored entry. The context is what the model receives next, after resets and compactions.
ResetClears what the model sees; the conversation, its id and its entries stay.
Agent run, model turnA run is the model turns from picking up an input until the conversation is idle or parked. A turn is one model request and its tool calls.
Worker threadOne unit of capacity; one active agent run uses one. A slot in the daemon, not an operating-system thread. Their count is S-000's limit on agents working at once.
WorkspaceA registered local folder an agent works in. It supplies extra instructions and skills and is where tools start.
Daemon, instanceThe single long-running process (bob serve). An instance is one daemon with its state directory; two instances share nothing.
DatabaseThe one pi-durable store of an instance: conversations, entries, pi-durable tasks, submissions and documents, plus the daemon's own documents.
Client, listenerA client is a separate program that uses the daemon and holds no work. A listener is a transport that exposes service operations to clients; none authenticates callers.
Service layer, operation, callerThe only way to read or change daemon state from outside the harness. An operation is one named capability, either read or control. The caller (client, job source or agent tool) states the actor that is recorded.
Observation feedThe stream of changes for a scope: a snapshot, then deltas.
SupervisorThe operating system's startup manager (systemd, launchd) that starts the daemon at machine startup without a login and restarts it on an error exit.

The planned scopes are the current intention, not commitments; each is fixed when its spec is approved. The task column is a snapshot at the review date; the tracker (ai-team list tasks --spec S-nnn) is the truth.

Open items that cross specs

  • The Jobs spec is the largest gap: S-001 relies on it for creating jobs, blocking and answering, and verification and closing. The run history a schedule passes to its next run belongs to the schedules and triggers spec.
  • How the choice is made between continuing a parked agent on each report or after the last: decided later. Until then a parked agent continues on each report (S-001 R-8a).
  • The packaging form (npm tarball or bundle with Node), starting at boot on macOS without a login, and retention of old conversations.
  • The standing decisions in section 1 are recorded: ADR-001 (one daemon, one database, pi-durable behind a host) and ADR-002 (equal team members with no logins, no approval rules, the service account as the boundary). ADR-003 and ADR-004 record how host commits and inputs sent on someone's behalf reach pi-durable.
