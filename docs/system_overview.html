The Intern: system overview

The Intern is one daemon that runs every conversation of one user in one pi-durable database. Agents made from roles take turns in those conversations and invoke each other. Clients, schedules and agent tools all use the same service layer. This document is the map: the shared vocabulary, the shape of the system, and which spec owns which part.

Specs and accepted ADRs win over this document contains no requirements updated with every spec that changes a shared term or the spec map

1 · Scope and principles

One user, one machine, one process

The Intern is an office assistant for a single person on their own computer. It is one TypeScript package that embeds pi as a library on @earendil-works/pi-durable.

In scope

  • One user and one OS account, on Linux (x64) and macOS (Apple silicon).
  • Work arrives from interactive chat, scheduled prompts and manual requests.
  • Local clients first; a LAN dashboard is planned, read-only at first.

Out of scope

  • Several users, remote callers, devices or hubs.
  • Windows, Linux arm64 and Intel macOS.
  • Compatibility of the database across pi versions; the pi packages are pinned.

Principles that hold across all specs

PrincipleWhat it means
One owner per databaseAt most one daemon opens an instance's database. Nothing else reads or writes it; clients read history through the service layer.
Durability belongs to the runtimeResume, exactly-once input, queued input and checkpoints come from pi-durable. We write no retry loops, intake tables or recovery code.
Filesystem permissions are the boundaryDirectories are 0700, files owner-only, no credentials are stored by us. Models authenticate through the user's pi login.
pi-durable sits behind a narrow hostOnly the host module and our own pi-durable extensions import it. An upgrade touches a few files.
Transport-free service layerEvery capability is a named operation marked read or control. A new listener never changes an operation.
Clients are viewersNo connection owns work. Closing or lagging never stops or slows an agent run.
Agents are peersNo agent owns another or a conversation. An agent of any role can hand off to, or invoke, any role.
Unattended by defaultOutside interactive chat, no step waits for a human.
Fail closed on the membraneInvalid configuration stops startup; a storage error ends the process and the supervisor restarts it. Missing content (a skill) degrades with a diagnostic.
2 · The system at a glance

Everything goes through the service layer

The daemon is the only process that touches the database. Chat, schedules and agent tools are different callers of the same operations.

3 · Roles, agents and conversations

A role is the base context; an agent applies it in a conversation

  • Every conversation has exactly one agent at a time.
  • A role defines the context where an agent starts.
  • The agent can only exist within a conversation.
  • An agent is mutable: it can be configured during the conversation.
  • Agents change by handoff (same conversation) or spread by invocation (new conversations).
  • Nothing here is an operating-system process.

Shared terms

These terms mean the same in every spec. A spec may add terms of its own and may refine one of these only by saying so in its Definitions.

Project terms

TermMeaning
the-internThe product. It runs as a daemon.
bobThe name of a role and of the CLI (bob chat, bob serve).
UserThe single person who talks to the-intern's conversations, configures and monitors it.
RoleThe base context an agent starts from: instructions, tools, skills and default model, thinking level and workspace.
AgentThe application of a role in a conversation, and the actor that interacts with the model there. It exists only within a conversation, one at a time, and can be configured during it. Not an operating-system process.
SeatThe place of the current agent in a conversation, with its role, model, thinking level and workspace (defaults or overrides).
ConversationThe pi-durable meaning: an ordered transcript of entries with its own pi-durable agent.
Transcript, contextThe transcript is every stored entry. The context is what the model receives next, after resets and compactions.
ResetClears what the model sees; the conversation, its id and its entries stay.
Agent run, model turnA run is the model turns from picking up an input until the conversation is idle or parked. A turn is one model request and its tool calls.
Worker threadOne unit of capacity; one active agent run uses one. A slot in the daemon, not an operating-system thread.
JobThe work an agent run is expected to complete. It can pass between agents.
WorkspaceA registered local folder an agent works in. It supplies extra instructions and skills and is where tools start.
Entry point, originWhat starts a conversation (chat for the root, a schedule fire, a user request). The origin records which one, or the invoking conversation.
Daemon, instanceThe single long-running process (bob serve). An instance is one daemon with its state directory; two instances share nothing.
DatabaseThe one pi-durable store of an instance: conversations, entries, pi-durable tasks, submissions and documents, plus the daemon's own documents.
Client, listenerA client is a separate process that uses the daemon and holds no work. A listener is a transport that exposes service operations to clients.
Service layer, operation, callerThe only way to read or change daemon state from outside the harness. An operation is one named capability, either read or control. The caller (client, entry point or agent tool) states the actor that is recorded.
Observation feedThe stream of changes for a scope: a snapshot, then deltas.
SupervisorThe operating system's service manager (systemd user service, launchd agent) that starts and restarts the daemon.

5 · Spec map

Which spec owns what

Specs are written in layers. Each one builds on the ones before it, and only S-001 and S-002 exist so far.

The planned scopes are the current intention, not commitments; each is fixed when its spec is approved. The task column is a snapshot at the review date; the tracker (ai-team list tasks --spec S-nnn) is the truth.

Open items that cross specs

  • S-002's startup (R-2 step 6) and operation catalogue (R-12) use S-001 pieces, while S-001 phase 1 waits on S-002 phases 1 to 3. The order of the two breakdowns is undecided.
  • When a parked agent continues (on each report or after the last) and what happens to a prompt sent to a parked conversation: left to the job spec.
  • User customisation beyond a workspace's instructions and skills. One candidate to explore: spawning pi agent sessions (not pi-durable agents) in a workspace, so the user's pi extensions apply. Not specified yet; S-001 and S-002 only exclude loading discovered extensions into the daemon.
  • The packaging form (npm tarball or bundle with Node), and retention of old conversations.
  • No ADRs exist yet for the standing decisions in section 1 (one daemon, one database, pi-durable behind a host).
