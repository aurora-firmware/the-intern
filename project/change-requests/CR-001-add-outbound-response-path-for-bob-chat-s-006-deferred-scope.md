# Add outbound response path for bob chat (S-006 deferred scope)

> **Superseded (2026-06-23):** S-008 was superseded by CR-002 (interactive chat
> moves to a supervised direct `pi` session whose output reaches the terminal
> directly), so this admin-socket outbound-path change request is obsolete.
>
> **Resolution (2026-06-11):** accepted at Gate 1 as spec S-008, now archived at
> `project/specs/archive/S-008-outbound-chat-response-path-over-the-admin-socket.md`.
> Decisions: multiplex on the subscription connection (per-service registry
> rejected); CLI `--session` maps to `context_id` (the `session` wire field is
> retired); delivery contract only — reply generation stays Phase 2 work.

## Desired Changes

Give `bob chat` a working outbound response path so an interactive session
is genuinely two-way:

- `chat.open` must establish a real push channel for the subscription it
  returns, so chat replies generated by the service are delivered to the
  subscribed client as JSON-RPC notifications (the pattern already used by
  `audit.tail.subscribe`).
- The client must be able to both send `chat.send` requests and receive
  reply notifications over the same subscription connection without the two
  interfering (PR #19 added notification buffering on the client; the server
  side of the contract is the missing half).
- Session routing must become meaningful end to end: the `session` value the
  CLI sends with `chat.open`/`chat.send` is currently ignored by the server,
  so `bob chat --session X` silently does nothing. The change must either
  honor it, map it onto the server's existing `context_id`, or remove the
  flag — `[TODO: decide which, during spec work]`.

## Context

Root-cause analysis on GitHub issue #16
(https://github.com/aurora-firmware/the-intern/issues/16) identified three
bugs behind the `bob chat` failure. Bugs 1 and 2 (missing `params.id`;
`chat.send` issued on a fresh connection that the per-connection
subscription registry rejects) are fixed by PR #19 / B-008. Bug 3 remains:
the subscription is hollow. `handle_chat_open` in
`crates/admin-rpc/src/dispatch.rs` returns a plain RPC response rather than
the subscribed outcome that creates a push channel, and the chat-adapter bus
receiver is dropped, so nothing can ever push a notification to the chat
client — `subscription.recv()` pends forever.

This is deliberate deferred scope: S-006 states interactive chat is
"inbound-only (effectively one-way) until the outbound-response spec
lands". This change request asks for that deferred scope to be picked up.

A design tension must be resolved by the spec: `AdminClient` subscriptions
are registered per-connection, while chat needs send and receive on one
session. The RCA names two candidate directions — multiplex send and
notification-read on the subscription connection (the direction PR #19's
client work already leans toward), or move the subscription registry from
per-connection to per-service scope. `[TODO: direction to be chosen in the
spec, with Architect input]`

## Potential Impact

- `crates/admin-rpc` dispatch and connection registry: `chat.open` outcome
  handling, possibly registry scoping for all subscription types
  (`audit.tail.subscribe` shares this machinery — regression risk).
- `crates/chat-adapter`: must route replies onto the per-subscription push
  channel instead of dropping the bus receiver.
- `crates/bob` CLI client: two known latent client-side issues become
  reachable once chat notifications actually flow, and should be addressed
  alongside or before this work (both flagged in PR #19 review):
  - `Subscription` reads are not cancellation-safe inside the chat
    `tokio::select!` loop (partial frames can be lost on cancellation).
  - the `session`/`context_id` mismatch described above.
  - if the protocol ever adds server-initiated *requests* (frames with both
    `method` and a non-null `id`), the client's `is_notification` classifier
    and `recv()` treat them as responses and reject them; the spec must
    either keep ruling such frames out or extend the client frame handling.
- S-006 acceptance criteria written around one-way chat may need revisiting.

## Possible Spec Amendments

- Amend S-006 to remove the inbound-only limitation, or supersede it with
  the new outbound-response spec it anticipates (recommended: new spec,
  since this adds a server push capability and a routing decision rather
  than rewording existing requirements).
